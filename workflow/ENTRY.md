# Codex 主会话接入本地工作流

本文件指导已获用户授权的协调者接入服务，不新增权限。使用前读取 README.md，并核实本机服务地址、token 文件、目标项目及会话绑定。

1. 与用户讨论需求。确定原始请求的稳定消息标识；宿主不给消息 ID 时生成一次并保存。不要把所有闲聊自动创建成任务。
2. 将人类原文通过 cli.ts POST /api/messages 登记，source=codex，使用真实 conversation_id，启用 intake 时先保存返回的 message.id；识别后再读取其 requirement_id，不能因回执暂时没有需求 ID 再建一单。问候不创建需求，补充关联原需求，归属不明确时先澄清。工具回执成功才算入库。
3. 在已有授权范围内整理 title/goal/scope/acceptance/questions，携带 revision 保存分析。或由已配置的分析会话自动分析。
4. 拆分任务必须以独立可验收的结果为单位。每项包含 deliverable、acceptance、dependencies、resources 和可选 worker_key；不得把扩大权限、部署或外部发消息隐含在任务中。
5. 展示需求和任务计划，遵循最新人类授权。匹配本机 automation 项目策略时允许服务自动确认并推进；否则 /approve 只确认当前 revision，不得拿旧确认批准新范围。
6. 后台服务已启用且绑定执行适配器时自动领取满足依赖、会话和资源条件的任务。若由原生聊天工具发送，则只选择一种发送路径，原生调用者先 /claim，再登记 started/report；不得与自动适配器同时发送同一个 run。
7. 核验实际执行来源、run、验收证据，再提交 review。模型的完成声明不能代替验证；automation 模式使用独立 verifier 会话检查实际产物。子任务通过后仍需核对整体需求。
8. 结果通告时读取 /api/outbox 中 source=codex 的 available 结果，在当前主会话正常回复。飞书由结果发送适配器负责。没有配置适配器时明确说明待接通，不冒充已送达。

暂停只阻止新的领取。结果不确定时保留 run 和资源，先检查原始聊天，使用原 run/token 附核对证据，不重建请求、不盲目重发。token 是本机访问凭据，不应写入提示词或日志。

控制器发来的既有任务使用它提供的 result_mailbox.py 本地回传命令提交结构化结果，最终聊天用正常文字说明交付与验证，不直接输出协议 JSON。回传缺失则核对原执行，不重新提交研发。已计划或执行的需求收到补充会暂停后续分发；未执行计划可核对后重新分析，已执行任务须先在主会话决定变更范围。


## 直接协调模式与工作流开关

用户明确说“这次不用工作流／直接协调”时，本次新需求不登记工作流，不修改团队长期设置。持久开关通过 `/api/teams/TEAM/workflow` 的 enabled 布尔值控制，board.teams 的 workflowEnabled 是当前状态。先根据真实入口聊天、来源和项目确定团队；不要把任意默认团队当当前入口。团队关闭时，新需求使用直接协调模式，不绕过已登记任务的状态或权限。

直接协调仍可在明确人类授权下用原生 list_threads/read_thread/send_message_to_thread/wait_threads 操作已有聊天；核实真实标题、ID、cwd、活动状态及文件边界。发送前核对未完成工作流和资源占用，存在重叠先交接，不对同一任务双重派发。保留最新用户要求，结果返回后核实证据并正常汇报；不强制六阶段登记、拆分或独立验收协议。不自动改模型、创建聊天或扩大部署权限。

已有工作流任务即使被要求临时绕过，也不能另建一份直接派发；先处理原任务的安全停止或交接。关闭团队只阻止新登记及后续领取，已发出的结果仍回收，通知继续交付。全局与团队暂停状态不被开关重置。若配置了 Bridge 团队台账路径，Bridge 会读取持久开关：团队关闭时新飞书消息进入绑定的 Codex 聊天，Workflow 服务可以不运行；已安全暂存但尚未登记的工作流消息会在关闭后转入 Bridge 队列。台账无法读取时继续缓冲，不能把服务故障当作用户选择了绕过模式。
